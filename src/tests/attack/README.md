# 攻撃試験

「攻撃を防げるか」を、侵入の成否ではなく **被害の上限** で確かめる
試験の置き場所。箱の前提は「アプリは乗っ取られ済み」なので、攻撃が
成功すること自体は失敗ではない。失敗は、被害が宣言の範囲（範囲・
対象・回数）を超えること、jail の外に届くこと、永続化すること。

## 試験一覧

- `app-rce/` — 本命。題材アプリに意図的な eval の穴を開けた
  「脆弱なアプリ」を通常経路（adapter → FastCGI → スロット）に
  置き、攻撃者の PHP コードをスロットの中で走らせる。中継の
  対象・予算の強制、ネットワーク無し、非永続、ホスト無事を
  `verify.sh` が判定する。
  実行: `sh tests/attack/run.sh`（段階0の起動・配置・後片付け込み）
- `cve-2012-1823-php-cgi/` — php-cgi の古典的 RCE（パッチ前
  5.3.11）を CGI モードで実際に発火させ、スロット相当の jail に
  収まるかを見る。箱の通常経路（FastCGI）では発火点に届かない
  理由も README に書いてある。
- `react2shell-cve-2025-55182/` — React Server Components の
  未認証 RCE（いわゆる node2shell）。脆弱な Next.js を jail で
  動かし、OS 層の封じ込めだけを見る（中継の強制は app-rce の
  担当）。ペイロードは公開 PoC を poc.local.sh に差し込む分担で、
  本体はリポジトリに入れない。

## 進め方の約束

- 脆弱なコードとパッチ前バイナリは、この階層と検証用ルート
  （/var/jails/vuln-*）にだけ置く。通常の slotbase / アプリには
  混ぜない。
- PoC は公開されているものの形をそのまま使う（伝送路の都合で
  割り切る場合は、その旨と理由を各 README に書く）。
- 判定は PASS / FAIL の一覧で出し、FAIL は設計への指摘として
  扱う（試験側を黙って直さない）。
